# Harness: двухкомитетный цикл разработки

Спецификация цикла разработки с AI-оркестрацией. Версия 1.0, утверждена
разработчиком 2026-10-29. Источник дизайна:
`ai_assisted_development_v1_0.md` (адаптирован под соло-разработчика после
трёх раундов консультаций с квантовыми партнёрами).

## 1. Принципы

- Двухуровневая абстракция: root-сессия проекта оперирует высоким уровнем
  (roadmap, контракты, статусы), субагент-исполнитель - только низким
  (один пункт, один модуль, свой контракт и файлы).
- Контракт-first: модуль определяется внешним контрактом до кода;
  исполнители разных модулей могут работать параллельно и независимо.
- Пункт roadmap = автономная задача = артефакт на выходе.
- Человеческие чекпоинты: утверждение roadmap (и sign-off контрактов)
  до кода, мерж релиза в конце. Мерж этапных PR - сама сессия при
  объективном гейте (approve code owner + зелёные checks). Всё между -
  автономно.
- Качество = тесты прошли + ревью пройдено. Оперативных метрик нет;
  сырой лог для ретроспективы.

## 2. Роли и комитеты

### Архитектурный комитет

Проектирует roadmap.md и дизайн каждого пункта.

- Devin-root (сессия в репозитории) - автор.
- gh-copilot-partner, gemini-product - соавторы-проектировщики
  (умные/дорогие модели).
- Разработчик - арбитр и финальный аппрув.

Споры соавторов: автор (Devin) выбирает вариант и логирует в блоке
`## Design Dissent` roadmap (`выбран A (Devin/Copilot) вместо B (Gemini),
потому что X`). Разработчик при аппруве видит все споры и может
переопределить. Голосования нет.

### Исполнительный комитет

Реализует один пункт roadmap.

- Devin-исполнитель (субагент профиля `code_writer`, узкий контекст) -
  автор кода. Профиль: `controller-manager/templates/code_writer.md`,
  экземпляр в каждом репо - `.devin/agents/code_writer.md` (рядом с
  git/hygiene/repository/reviewer).
- Контракт code_writer: PR/отчёт сдаётся только на зелёном нативном
  прогоне проекта (lint-entrypoint + tests + typecheck). Lint-конфиг
  живёт в нативных файлах проекта (pyproject.toml/package.json/Makefile)
  - харнесс только вызывает entrypoint, своего lint-конфига в .devin/
  нет и быть не должно.
- gh-copilot-partner, gemini-product - соавторы-консультанты
  (модели дешевле; консультация до спавна и по необходимости).

### Ревьюверы (вне комитетов)

- Судья пункта - субагент root-сессии, свежий ограниченный контекст,
  repo-доступ.
- Reviewer-субагент (профиль reviewer, different-badge) - уровень PR.
- Авто-ревью на MR (Copilot в репо по триггеру пуша; до возврата лимитов -
  quantum-partner на gemini дешёвой модели, настройка в shore-felidae).

Инвариант: одна сессия/субагент никогда не имеет и авторства, и аппрува.

## 3. Артефакты

### roadmap.md

Живёт в `.devin/` репозитория, НЕ публикуется (рабочий документ процесса:
живые статусы, вердикты, споры - не для дерева репо и не под правила
English-only/без-AI-имён публичных репозиториев). Доступен субагентам
локально.

- Header: решения по стеку/архитектуре/FE-BE границе (фиксируются до
  кода), индекс активных контрактов со статусами, глобальная команда
  приёмки, `## Design Dissent`.
- Пункты: шаблон `templates/roadmap.template.md`.

### КОНТРАКТ (объект)

- Файл `contract.py` (Pydantic v2) или `contract.ts` (типы + ajv/zod при
  необходимости runtime-валидации) - обычный исходник, коммитится в репо,
  колоцирован с модулем. Содержит вход/выход, ошибки, описание
  сайд-эффектов. Не вести центральную папку contracts/.
- Статус в roadmap.md: draft > judged > signed_off.
- Sign-off = явное "утверждаю" разработчика после прохода судьи.
- Implementation/test-пункты читают контракт read-only и не стартуют
  без signed_off.
- Изменение контракта - новый contract-пункт или PLAN_DELTA
  (что меняем + какие пункты инвалидируются) на approve/reject
  разработчика. Никогда не правка исполнителем по ходу.

### docs/specs/ (living spec)

Реестр актуального поведения системы - отвечает на вопрос "как
устроено сейчас". Публичный, English-only, коммитится в репо
(это документация системы, не процессный артефакт). Структура:
`docs/specs/<domain>.md` - одна область = один файл.

Формат требования - сценарный, совместимый с G/W/T:

```markdown
### Requirement: quota-park on explicit model limit
The bridge SHALL park a step on an explicit model rate-limit
error carrying a reset time.

#### Scenario: park until reset
- **WHEN** a step reports rate-limit error with reset_at
- **THEN** step_state becomes waiting_quota until reset_at
- **AND** retry budget is not consumed
```

Имена `Requirement` стабильны - на них ссылаются `.changes` и
проверки покрытия.

Обновление - только дельтами через `.changes/<slug>.md`:
обязательная секция `## Spec impact` со строками
`adds:` / `modifies:` / `removes:` - якорями вида
`docs/specs/<domain>.md#<requirement-anchor>` (bare `-` при
отсутствии поведенческого импакта). Дельта применяется в том же
PR, что и код - атомарно, spec и поведение не расходятся.
Проверка: якорная валидация в `verify_constraints.sh` / CI -
каждый якорь Spec impact обязан разрешаться в целевом файле
(защита от ссылок в никуда).

Границы: spec - поведение системы; roadmap - работа и статусы;
contract.py/ts - типы (spec ссылается, не дублирует); ADR -
решения и причины. Бэклог-идеи и непринятые планы в spec не
попадают - только то, что уже в коде.

Правило сессий: на вопрос "как устроено сейчас" сначала смотрится
`docs/specs/`, потом код. Расхождение spec<>код - дефект,
фиксится дельтой в ближайшем PR.

### harness_log.jsonl

В `.devin/` репо. Одна строка JSON на закрытый пункт, 7 полей:

```json
{"item_id": "item_03", "category": "implementation",
 "arch_revisions": 1, "exec_review_rounds": 2,
 "deviations_reported": {"autonomous": 1, "contract_escalations": 0},
 "model_tier_upgraded": false,
 "final_outcome": "merged_clean",
 "friction_note": "worker fought mock setup in tests"}
```

- category: contract | implementation | test | refactor | docs | exploration
- arch_revisions: итераций аппрува пункта в архкомитете
- exec_review_rounds: раундов судья/ревьювер (1, 2, 3+)
- model_tier_upgraded: был ли апгрейд моделей исполкома
- final_outcome: merged_clean | merged_with_human_edits | re-planned | abandoned
- friction_note: одна строка - что больше всего тормозило

Ретроспектива: после 15-20 пунктов лог уходит gemini-product на анализ
узких мест, тогда и появятся метрики.

### Модель сессии-директора (event-driven, утверждено 2026-11-11)

Сессия-воркер = директор проекта: не пишет код сам, поручает
фоновым исполнителям и живёт КОРОТКИМИ событийными ходами.
Цель: сессия почти всегда доступна для почты оркестратора и
вопросов - доступность достигается освобождением слота, а не
вечным удержанием.

Принципы:

- **Событийный ход**: директор просыпается только на событие -
  (A) письмо/директива оркестратора, (B) завершение/падение
  фонового исполнителя, (C) чекпоинт-тик мониторинга. Каждый ход
  завершается быстро: drain -> решение -> конец хода.
- **Лимит длины хода T** (дефолт 30 мин): ход длиннее T -
  архитектурная ошибка. Длинная работа = фоновый исполнитель +
  обязательные чекпоинты каждые T минут (обновить статус задачи,
  сдренить почту, продлить lease через `bridge wait`).
- **Один фоновый исполнитель в момент времени** (MVP): никакого
  параллельного зоопарка субагентов внутри сессии. Контракт
  исполнителя: `{task, context_slice, deadline, report_to}`;
  таймаут 20-30 мин на шаг; retry-cap - макс. 3 до эскалации.
- **Подпись кровью**: директор НЕ отчитывается по словам
  исполнителя - перед отчётом/мержем лично прогоняет
  `git status`/`git diff`/ключевой тест и верифицирует артефакт.
- **Kill-switch**: директива STOP от оркестратора - директор
  синхронно убивает фонового исполнителя ДО ответа на письмо.
- **Lease != прогресс**: `bridge wait` продлевает lease только
  при живом исполнителе (progress note с сутью, не пустой пинг).
- **Ревью - только внешнее**: директор никогда не спавнит
  reviewer на свой же PR - конфликт интересов. Reviewer-агент
  вызывается независимо (отдельная учётка ASKON-1989).
- **Mid-turn inject - факт закрыт эмпирически (2026-11-11,
  devin-session-bridge issue #137)**: `session/prompt` на занятой
  сессии отклоняется сразу ("a turn is already running") - не
  ставится в очередь и не инжектится. Событийная модель -
  единственный путь; 'always-on' недостижим.

### Версионирование и релизы

Политика версий фиксируется на этапе утверждения roadmap, а не при
мерже (решение разработчика 2026-11-11):

- **Тип релиза - в roadmap**: у каждого пункта поле `release: patch |
  minor | major` и `target_version: X.Y.Z`, назначаются и утверждаются
  вместе с планом. 1 функциональная фича - minor; 1 крупная фича
  (архитектурный сдвиг / ломающее изменение) - major; исправления,
  tooling, docs - patch. Версия резервируется за пунктом заранее -
  параллельные ветки не конкурируют за номер.
- **Ветка**: `issue_<N>_v<target_version>`; версия в
  `pyproject.toml`/`package.json` + `.changes/<slug>.md`-фрагмент
  обязаны быть на ветке ДО мержа PR (`failure_class=version_drift`
  иначе). Фрагмент обязателен в каждом PR с изменениями
  (tooling/chore - `user_visible=false`); мерж без фрагмента гейтится
  CI и `repo_merge.sh`.
- **Релиз**: после мержа ветки `repo_release.sh` сворачивает
  `.changes`-фрагменты в CHANGELOG и тегирует `target_version`.
  Несоответствие заявленного типа фактическому diff - замечание
  ревьюера.
- Канонические раскатки оркестратора: фрагмент + бамп в том же PR -
  ретроактивные бамп-PR недопустимы.

## 4. Жизненный цикл пункта

1. Архкомитет проектирует roadmap (пункты, типы, зависимости, контракты,
   стек/FE-BE, G/W/T, risk-флаги, Design Dissent) > аппрув разработчика.
   Для репозитория без CI roadmap ОБЯЗАН начинаться с infra-пункта:
   `.github/workflows/` - lint + tests (стек-эквивалент: ruff/pytest,
   eslint/vitest и т.п.), триггеры push в base-ветку + pull_request.
   До мержа CI-пункта критерий успеха - локальный прогон; после мержа
   зелёный CI обязателен на каждом PR.
2. ISSUES: после аппрува roadmap каждый пункт заводится отдельным issue
   в таск-трекере проекта (issues репозитория). Ссылки/номера issues
   записываются обратно в roadmap.md, имена веток и трекинг - по ним.
   Имплементация не стартует до заведения всех issues.
   Бэклог: идеи, отложенные находки, техдолг и исследовательские
   вопросы оформляются issue с меткой `backlog` - кандидат, ничего не
   гарантирует; пунктом roadmap issue становится только по аппруву
   roadmap и переживает перепланирования.
3. Contract-пункт: исполнитель пишет contract-файл > судья > sign-off
   разработчика (блокирующий чекпоинт).
4. Implementation-пункт:
   a. Пред-консультация партнёров по пункту: {текст пункта + контракт
      инлайн + 1-строчные саммари зависимостей} с вопросом "найди дыры
      в критериях и подводные камни стека, код не пиши". Ответ -
      структурированный JSON-список флагов; root приклеивает их к пункту
      как additional_acceptance_notes. Не для docs/refactor-пунктов.
   b. Спавн исполнителя с пакетом (п.5).
   c. Исполнитель (code_writer): scope-план > тесты из G/W/T + код >
      зелёный нативный прогон (lint+tests+typecheck проекта) >
      re-grounding (git status/diff --stat против scope-плана) >
      отчёт по формату профиля (RESULT/GATES/DECISIONS/OPEN).
      Отчёт без литерального статуса прогонов не принимается.
   d. Судья пункта верифицирует (п.5). Цикл доработок до вердикта.
   e. Строка в harness_log.jsonl.
5. Отклонения: неконтрактные - исполнитель решает сам, отчёт
   выбор+альтернативы; контрактные - эскалация (PLAN_DELTA >
   approve/reject).
6. Сборка PR (все пункты ветки done): интеграционный прогон
   reviewer-субагентом (перепроверка G/W/T каждого пункта + межпунктовая
   согласованность) > цикл доработок ДО вердикта APPROVE:
   REQUEST_CHANGES или COMMENT с блокирующими находками - исполнитель правит и идёт на новый проход. APPROVED выставляет только reviewer (self-approve не засчитывается); COMMENT человека/сторонних с одними MINOR трактуется как согласие.
   PR не готов к мержу без APPROVE. Если раундов ревью > 3 - жалоба
   архкомитету ("много циклов ревью, что исправить"), действие по его
   решению. Если архкомитет вызван по одному PR 3 раза и не смог снять
   возражения - стоп, эскалация к разработчику. После APPROVE -
   сессия сама мержит PR (approve code owner + required checks зелёные,
   пункт без manual_gate). Мерж релиза (тег + GitHub Release) - за
   разработчиком.

### Тип пункта exploration

Пункт roadmap до фриза критериев - для областей, где критерии приёмки
нельзя сформулировать, не исследовав предмет (прецеденты: аудио-
возможности Android, сигналы квоты транспорта).

- Артефакт на выходе - research-note: секция в roadmap или
  `docs/research/<slug>.md`. Содержит: что проверено, что
  подтверждено, что опровергнуто, открытые вопросы, рекомендацию.
- Критерий приёмки - НЕ код: перечень вопросов, на которые
  исследование обязано ответить, и границы метода (только
  документация / прототип-допустим / конкретные API) - поля
  `research_questions` и `method_bounds` в шаблоне пункта.
- Судья exploration-пункта проверяет полноту ответов на заявленные
  вопросы и соблюдение границ метода - код не оценивается.
- Зависимые contract/implementation-пункты получают `depends_on` на
  exploration-пункт и не фризят критерии до его вердикта.
- Exploration не пишет проектный код; прототип-заготовки - в
  `archive/` или scratch, не в основное дерево.
- Пред-консультация партнёров (п.4a) для exploration не выполняется -
  сам пункт и есть разведка.

## 5. Пакеты контекста (белые списки)

- **Исполнитель**: свой блок пункта roadmap; контракт read-only;
  may_edit/may_not_edit; acceptance-команда; 1-2 референс-файла;
  G/W/T сценарии; additional_acceptance_notes. НЕ видит: план целиком,
  чужие модули, reasoning архкомитета.
- **Исполнитель exploration-пункта**: `research_questions` +
  `method_bounds` + релевантные docs/исходники read-only. НЕ видит:
  план целиком, чужие модули.
- **Судья пункта**: текст пункта с критериями и G/W/T; путь к контракту
  (читает сам из репо - защита от рассинхрона); дифф пункта;
  kb_rules excerpt <=2KB по доменным тегам (python-backend / ts-express /
  react-mobx; отбор таблицей, не LLM). Может до 2 раз вызвать у root
  request_reference(topic) - root возвращает срез <=N строк <=M файлов.
- **Судья exploration-пункта**: `research_questions` + `method_bounds` +
  research-note артефакт. Проверяет полноту ответов на каждый вопрос и
  соблюдение границ метода - диффа нет, код не оценивается.
- **Reviewer-субагент (PR)**: URL PR + artefact_paths + путь к контракту +
  тексты пунктов с критериями/G/W/T + kb_rules excerpt + предыдущий
  вердикт при ре-ревью. Потолок ~4KB без диффа. Обязан перепроверить
  покрытие сценариев по каждому пункту.
- **Партнёр-консультант** (нет repo-доступа): инлайн {текст пункта,
  контракт целиком, саммари зависимостей, вопрос}. Структурированный
  ответ обязателен.
- **Resolver** (застрявшее ревью): пункт + контракт + дифф + история
  возражений + чтение всего текущего репо (без кросс-репо).

## 6. Лестницы эскалации

### Спор с ревьювером

Ревьювер прав по умолчанию - исполнитель исполняет. Триггер эскалации:
несогласие исполнителя ИЛИ ревьювер пометил возражение `uncertain`.
Вопрос - ОБОИМ партнёрам сразу. Сошлись - закрыто; разошлись -
разработчику. Подлесенок нет.

### Застрявшее ревью

- Раунды 1-2: обычный цикл исполнитель-судья.
- Не сошлись после 2-го раунда: resolver-субагент (последняя
  автоматическая попытка, НЕ сброс счётчика).
- Resolver не свёлся или истёк 3-й раунд: стоп + классификация:
  - повторяющийся класс возражений - подход неверен: апгрейд моделей
    исполкома, переделка пункта;
  - спор о смысле критерия - неопределённость спеки: архкомитет
    уточняет G/W/T;
  - разнородные мелкие возражения - перекалибровка судьи.

### Risk-флаг (ставится в roadmap при планировании)

Пункт трогает контракт/schema-файлы, auth/persistence-границы или >1
модуля - автоматически два вердикта ревью разных семейств моделей +
подтверждение разработчика перед сборкой PR.

## 7. Конвенции тестов

- Стек: Vitest для TS/JS (ESM type:module, Node 24, единый фреймворк с
  om_ws_fe), pytest (+pytest-asyncio) для Python.
- Файл теста рядом с исходником: `foo.test.ts` / `test_foo.py` по
  конвенции репо.
- Имя теста содержит id сценария verbatim:
  `it('[ITEM-12.GWT-3] returns 409 on duplicate')`. Обязательное правило;
  в CI - grep id из roadmap.md против тестов.
- Один тест = один сценарий G/W/T.
- Моки - на границе контракта (HTTP-клиенты, репозитории БД через
  интерфейс модуля); мок реализует тип из contract.ts/py. Запрещено
  мокать внутренние вызовы тестируемого кода.
- Тесты и реализация - в одном коммите; при правках обновляются атомарно.

## 8. Root-дисциплина

- Root держит высокий уровень: roadmap, статусы, индекс контрактов.
  Repo-доступ есть (нужен для постановки и ответов на вопросы).
- Больше 2-3 файлов или repo-wide поиск - read-only research-субагент,
  в контекст root идёт только выжимка.
- Re-ground к roadmap.md перед стартом каждого пункта.
- Все решения сразу в roadmap.md - root перезапускаем без потерь.
- Проектный код root не правит. Застрявшее ревью - resolver-субагент,
  не самостоятельная починка.

## 8.1. Старт сессии - протокол инициализации

Выполняется ОДИН РАЗ при старте сессии, до любой работы кроме чтения
`.windsurfrules` и явно названных файлов. Это условия входа, а не
согласование каждого шага: после инициализации действуют только
гейты цикла (аппрув roadmap, sign-off контрактов, PLAN_DELTA, споры
ревью) - промежуточных подтверждений не требуется.

1. РОЛЬ: сформулировать свою роль и ожидаемый результат. Если
   назначение сессии из правил/контекста неочевидно - уточнить у
   разработчика одним вопросом.
2. СКИЛЫ И ИНСТРУМЕНТЫ: проверить харнесс - `partner_info` по обоим
   партнёрам, профили в `.devin/agents/`, скилы в `.devin/skills/`.
   Если для задачи критично чего-то не хватает - спросить у
   разработчика, чем заменить или где взять. Молчаливые замены
   запрещены.
3. ЗАДАЧА: если постановка задачи не передана в первом сообщении -
   спросить у разработчика, какая задача у сессии, и ждать ответа.
   Самостоятельно выбирать предмет работы и анализировать репозиторий
   "на всякий случай" запрещено. Исследование кода допустимо только
   после постановки - и только в объёме, нужном для roadmap и
   уточняющих вопросов.
4. ROADMAP: формировать roadmap.md только по прямому указу
   разработчика ("составь roadmap", "строй план"). Постановка задачи
   сама по себе указом на roadmap не является - до указа можно
   задавать уточняющие вопросы, нельзя генерировать документ.

## 9. Состояния шагов, квота и наблюдаемость

### 9.1. Формат отчётности (краткий инвариант - в правилах сессий)

- Каждый авторский текст, включая промежуточные сообщения о ходе
  работы, начинается с `YYYY-MM-DD HH:MM` и маркера
  `Вопрос -` / `Задача -` / `Ответ -`.
- Сообщения о ходе работы дополнительно содержат строку статуса:
  `Шаг: <что делается> [<состояние>]`.

### 9.2. Состояния шага (долговременные)

Шаг - единица работы внутри задачи (пункт roadmap, вызов ревьюера,
публикация). Состояния:

- `running` - выполняется;
- `interrupted` - оборвано без сохранения точки (сбой хода, kill);
- `waiting_quota` - припарковано по явной ошибке лимита модели;
- `saved` - точка продолжения сохранена, шаг не выполняется;
- `paused` - остановлено внешней командой (HALT, ручная пауза).

Сессия обязана уметь ответить на запрос статуса состоянием текущего
шага, временем последнего обновления и причиной перехода.

### 9.3. Протокол лимита модели (waiting_quota)

Триггер - ТОЛЬКО явная ошибка квоты/лимита модели с временем сброса
(например, "Reached free model rate limit ... reset at HH:MM UTC").
`rpc_error`, `busy`, lease expiry, таймауты - НЕ квота.

При триггере:

1. Зафиксировать: текст ошибки, источник (root / subagent / partner),
   `reset_at` в UTC, модель/пул если известны.
2. Сохранить точку продолжения шага (что сделано, что осталось,
   артефакты/ветка).
3. Перевести шаг в `waiting_quota` до `reset_at`. Задача НЕ
   проваливается, бюджет попыток НЕ расходуется, lease-восстановление
   не порождает второго исполнителя.
4. До `reset_at` wake-сообщения в сессию подавляются.
5. После `reset_at` - одна контрольная проба (preflight ping модели
   внутри сессии перед возобновлением шага):
   - успех > продолжить ровно заблокированный шаг;
   - снова лимит > обновить `reset_at`, повторный цикл ожидания
     (без частых повторов).
6. HALT флота имеет приоритет: сброс квоты не возобновляет
   остановленную работу.

Рабочая модель: лимит привязан к модели/пулу, форма вызова
(root или subagent) не важна - проба на одной точке отражает пул.
Если наблюдение опровергнет (root прошёл, subagent упал) -
разделить пулы.

### 9.4. Дедупликация пробуждений

Wake/nudge сессии засчитывается только если есть И подтверждение
доставки, И фактическое продвижение (новое сообщение/статус/прогресс
шага). N одинаковых wake без продвижения = 1 инцидент, не N попыток.
Занятую (`busy`) или квота-блокированную сессию повторно не толкать.

### 9.5. Ответственность

- Текстовый инвариант (9.1) - короткое правило в `.windsurfrules`.
- Эта спецификация - canonical harness, сюда ссылаются правила.
- Машинное хранение состояний и дедупликация - sessions-bridge
  (состояния задач/шагов, reset_at, suppress-window).

## 10. Что не входит (отрезано осознанно)

Мутационное тестирование, CRAP/когнитивные метрики, отдельный LLM-gate
в CI, DDD-тиеринг ревью, ephemeral-окружения, обязательные
C4/sequence-диаграммы, фазы Enrich/Research как отдельные этапы,
pre-commit хук на FROZEN-контракты, запрет root читать код, токен-капы
контекста, оперативные метрики успеха.
